A ShadowKV trace extension for LLMServingSim, estimating raw TTFT, TPOT, output throughput, and simultaneous-user capacity. Official-weight placement

Safetensor totals come from the official Hugging Face repositories. Stored weights are unpacked or converted inside fused kernels; BF16 activations and BF16 tensor-core compute are assumed, without retaining a full BF16 copy.

Kimi Code 2.7 595.2 GB INT4 · two nodes

The files technically occupy 93% of one node's nominal HBM, leaving too little runtime workspace. The estimate therefore uses eight contiguous TP2 stages—roughly 7–8 layers each—with four stages on each server.

GLM-5.3 755.6 GB FP8 · two nodes

The official checkpoint cannot fit in 640 GB. Eight contiguous TP2 stages—roughly 9–10 layers each—avoid expert all-to-all across IB; FP8 weights are converted to BF16 fragments as consumed.

DeepSeek V4 Flash 159.6 GB FP4/FP8 · one node

Two independent four-GPU replicas remain feasible. Mixed-format weights are converted in the matmul path and never expanded into a persistent BF16 model image.

Topology assumption: Kimi and GLM use PP8×TP2. Stages 1–4 are contiguous on server A and stages 5–8 on server B, so only the stage-4→5 BF16 activation crosses 400 Gb/s IB, modeled as 40 GB/s usable. The other six stage boundaries stay on NVLink. Cross-node expert parallelism is excluded.

FP8 KV-storage overlay

Exact/offloaded KV and the selected GPU working set use E4M3 plus one FP32 scale per 128 values. Attention still computes in FP16/BF16 after fused dequantization.

Bytes About 48.4% less KV traffic

One FP8 byte plus scale metadata costs about 1.031 bytes/value, versus 2 bytes/value for BF16. Host-cache capacity nearly doubles.

Ampere conversion Conversion is not free

A custom A100-SXM4 SM80 kernel measured 455 Gvalue/s for fused E4M3 block-scale conversion to BF16. The trace uses that center and samples 320–520 Gvalue/s; an unfused PyTorch cast-plus-scale path measured only about 80 Gvalue/s.

Admission Topology sets the ceiling

FP8 KV still saves cache bytes, but the admitted maxima now reflect eight-stage pipeline throughput for Kimi and GLM: 48/28/14 and 48/40/30 users at 72K/128K/256K.

What the ideal case says

Decode Concurrency becomes practical

Only 1.56% of the exact cache is consumed per decode step. With context sharding and overlapped prefetch, active batches can grow without keeping every request's full exact KV cache in HBM.

Prefill TTFT remains the bottleneck

ShadowKV does not remove the compute needed to process 128K or 256K prompts. A simultaneous cold-start burst can therefore wait minutes even when later token streaming is acceptable.

Pipeline Low load gets slower

A lone decoder traverses eight stages while only one two-GPU pair is active. Around 50–75% of the admitted batch, independent requests fill most bubbles; beyond that, contention and queue risk dominate.

Assumptions

“Perfect condition” means flawless execution of the stated design—not a magical oracle. The central advisory oracle has 80% recall and 80% precision and is verified by current-token landmark selection.

Hardware and runtime

  • Each node has 8× NVIDIA A800 80 GB, approximately 640 GB nominal aggregate HBM; Kimi and GLM consume two IB-connected nodes, while V4 Flash consumes one.
  • An A100-SXM4 proxy measured about 22.0 GB/s long-transfer H2D to one GPU but only 25.4 GB/s aggregate when both GPUs in a TP2 stage copied concurrently. The model enforces both ceilings, plus a still-assumed 180 GB/s node host-DRAM ceiling.
  • 400 Gb/s InfiniBand is modeled as approximately 40 GB/s usable one-way payload bandwidth. Stages 1–4 are on server A and 5–8 on server B, so pipeline parallelism crosses IB once per forward pass.
  • 1 TB system RAM per node, with exact caches sharded across GPU-local NUMA regions rather than replicated for every tensor-parallel rank.
  • Custom serving code, optimized kernels, static knowledge of all requests, and one model deployment at a time.

Model and ShadowKV behavior

  • Official Hugging Face storage formats are retained: Kimi native INT4, GLM FP8, and V4 Flash mixed FP4/FP8. Fused kernels dequantize into registers/shared memory and compute in BF16; no persistent BF16 weight copy is allocated.
  • Exactly 1.56% of context entries are selected: 1,152 at 72K, 2,048 at 128K, and 4,096 at 256K.
  • Temporal reuse retains 60% of the selected set. Over the remaining 40%, the one-token-ahead oracle has 80% recall and 80% precision: it prefetches 0.40× the selected set and leaves 0.08× for just-in-time materialization.
  • The current query still runs landmark selection to verify the required set and discover oracle misses. Only prefetch and reconstruction that finish before their consumer are hidden.
  • Every cache-bearing transformer block is charged separately, following ShadowKV Table 13's causal order: select → max(reconstruct K, fetch V) → sparse attention.
  • No quality degradation from sparse selection and no pathological attention pattern that defeats the predictor.
Simulation boundary: the pinned LLMServingSim code supplies its vLLM-compatible transformer-block partitioning: Kimi's 61 cache blocks split 7/7/8/8/8/8/8/7 and GLM's 78 split 9/10/10/10/10/10/10/9. This repository adds ShadowKV events externally because stock tiered-KV recall does not represent landmark selection or low-rank key reconstruction.

Why the models differ

The same 1.56% policy interacts with three substantially different attention/cache designs.

Kimi Code 2.7

Largest decode-side upside

Its dense MLA-style long-context attention still pays heavily for cache access. The 595.2 GB native-INT4 checkpoint is too tight for a practical one-node runtime. With the PP latency floor enforced, the 80/80 oracle leaves full-load FP8 centers at 4.9/4.4/3.8 tok/s per user for 72K/128K/256K.

Planning cache: about 4.8/8.6/17.2 GiB exact CPU cache per 72K/128K/256K request. With one eighth of the layers on each TP2 stage, the selected GPU representation scales from 1,152 to 4,096 entries per layer.

Method and interpretation

How the displayed metrics are derived

per-user throughput = aggregate output throughput ÷ active requests TPOT (ms/token) = 1000 ÷ per-user throughput average burst TTFT ≈ pipeline-aware single-prompt TTFT × (requests per replica + 1) ÷ 2 average 512-token completion = average TTFT + 511 × TPOT

For Kimi and GLM, the single-prompt center includes chunked PP8 overlap during prefill; they each remain one logical model replica. Decode cannot pipeline successive tokens from one user because of the autoregressive dependency. Flash has two replicas. The scheduler prioritizes first tokens.

Metric definitions

TTFT
Time from admission until the first generated token, including prompt prefill and queueing inside the closed burst.
TPOT
Steady-state time between generated tokens after prefill.
Total tok/s
Tokens produced by the entire model deployment across all active requests—two nodes for Kimi/GLM and one node for V4 Flash.
Per-user tok/s
Fair-share generation rate for one continuously decoding request.
100% load
One closed batch at the chosen admission ceiling—not stable 100% arrival-rate utilization.
Queueing warning: at sustained 100% offered utilization, mean queue delay has no finite bound. A real service needs admission control, prompt-length-aware scheduling, and reserved prefill capacity even if every request is known in advance.

Detailed estimation model

The expandable derivation makes every major scaling assumption explicit and separates calculated quantities from calibrated performance estimates.

Show the mathematical model and model-specific reasoningOfficial weight bytes, PP8×TP2, selection, pipeline bubbles, PCIe/IB traffic, throughput, TTFT, and queueing

1. Sparse working-set size

Let \(N\) be the prompt length, \(\alpha=0.015625=1/64\) the selected fraction, \(L\) the number of cache-bearing layers, \(P\) pipeline stages, \(d_c\) the exact cached latent width, \(b=2\) bytes per FP16/BF16 element, and \(G_s\) GPUs per stage. The selected entries per decode token are

\[ S(N)=\alpha N, \qquad S(131{,}072)=2{,}048, \qquad S(262{,}144)=4{,}096. \]

The useful selected-cache payload after ideal context sharding is

\[ B_{\mathrm{sel,stage}}(N)=\frac{S(N)\,(L/P)\,d_c\,b}{G_s}. \]

2. Oracle recall, precision, reuse, and PCIe traffic

Let \(r=0.60\) be temporal reuse from the preceding token, \(R_o=0.80\) oracle recall, and \(P_o=0.80\) oracle precision, all measured over entries not already resident. This separates useful coverage from false-positive traffic:

\[ B_{\mathrm{prefetch}}=(1-r)\frac{R_o}{P_o}B_{\mathrm{sel}}=0.40B_{\mathrm{sel}}, \qquad B_{\mathrm{JIT}}=(1-r)(1-R_o)B_{\mathrm{sel}}=0.08B_{\mathrm{sel}}. \]

The total newly materialized traffic is 0.48× the selected set, versus 0.40× for fetch-at-decode with the same reuse. Prefetch is allowed to overlap the preceding token, but the selector and the 0.08× just-in-time miss set remain on the current token's critical path. The measured proxy provides about 22.0 GB/s to one GPU and 25.4 GB/s aggregate to both TP2 GPUs, so

\[ t_{\mathrm{JIT,TP2}}\approx\max\!\left( \frac{B_{\mathrm{JIT,GPU}}}{22.0\ \mathrm{GB/s}}, \frac{2B_{\mathrm{JIT,GPU}}}{25.4\ \mathrm{GB/s}} \right). \]

3. Memory and admission capacity

For admitted concurrency \(C\), the simplified per-node HBM and host-memory constraints are

\[ M_{\mathrm{HBM,node}} \approx \frac{M_W}{N_{\mathrm{node}}} + M_{\mathrm{runtime}} + C\frac{M_{\mathrm{shadow}}(N)}{N_{\mathrm{node}}} \le 640\ \mathrm{GB}, \] \[ M_{\mathrm{CPU}} \approx M_{\mathrm{staging,node}} + C\frac{M_{\mathrm{exact}}(N)}{N_{\mathrm{node}}} \le 1\ \mathrm{TiB}. \]

Here \(M_W\) is the actual official safetensor total: 595.2 GB for Kimi native INT4, 755.6 GB for GLM FP8, and 159.6 GB for V4 Flash mixed FP4/FP8. Kimi and GLM use \(N_{\mathrm{node}}=2\), \(P=8\), and \(G_s=2\): four stages per node. V4 Flash uses two independent four-GPU replicas, \(R=2\), on one node. \(M_{\mathrm{runtime}}\) covers activations, communication buffers, kernels, and allocator headroom.

The displayed “max” is not the largest integer satisfying memory alone. It is an admission ceiling chosen at the earlier of the memory limit and the throughput knee:

\[ C_{\max}= \min\!\left( C_{\mathrm{HBM}}, C_{\mathrm{DRAM}}, C_{\mathrm{PCIe}}, C_{\mathrm{knee}} \right). \]
Resulting admission ceilings

Kimi: \(C_{\max}=28/14\), GLM: \(C_{\max}=40/30\), and V4 Flash: \(C_{\max}=64/48\) for 128K/256K respectively. These are throughput/latency admission knees, not the largest values that fit in memory.

4. LLMServingSim trace extension and throughput

The extension follows LLMServingSim's trace structure and imports its transformer-block PP partitioner for stage ownership. Because upstream has no A800 profiles for these frontier models, the non-ShadowKV floor \(T_{\mathrm{core}}\) remains a calibrated input rather than an upstream prediction. For every cache-bearing block \(\ell\), the extension emits selection, background prefetch, miss materialization, and optional FP8 dequant events. The causal critical path is

\[ t_{\ell}=t_{\mathrm{select},\ell} +\max(t_{K,\ell},t_{V,\ell}+t_{\mathrm{dequant},\ell}) +t_{\mathrm{attention},\ell}, \] \[ T_{\mathrm{step}}=T_{\mathrm{core}} +\sum_{\ell=1}^{L}\!\left[t_{\mathrm{select},\ell}+t_{\mathrm{materialize},\ell}\right] +\max(0,t_{\mathrm{prefetch}}-t_{\mathrm{overlap}})+t_{\mathrm{PP/IB}}. \]

The total and fair-share output rates then follow directly:

\[ Y_{\mathrm{total}}(C,N)=\frac{C}{T_{\mathrm{step}}(C,N)}, \qquad Y_{\mathrm{user}}(C,N)=\frac{Y_{\mathrm{total}}(C,N)}{C}, \qquad \mathrm{TPOT}=\frac{1000}{Y_{\mathrm{user}}}\ \mathrm{ms}. \]

For PP placements, the raw load calibration is bounded by the one-user autoregressive recurrence. Pipeline fill is treated as a capacity effect, not an inverse latency multiplier:

\[ T_{\mathrm{ref}}(C)= \max\!\left[T_{\mathrm{ref,raw}}(C),T_{\mathrm{ref,raw}}(1)\right], \qquad P>1. \]

ShadowKV Table 13 reports per-transformer-block selection of 0.80 ms and materialization \(\max(1.36,1.66)=1.66\) ms at 24×128K. These terms are scaled by active sequences, context, cached width, reuse, and storage precision. Unlike the earlier page revision, materialization is multiplied by every cache-bearing block. A deterministic 256-sample sensitivity run varies PCIe, host DRAM, dequant throughput, selector timing, and materialization timing; its p10–p90 range is a parameter-sensitivity interval, not a confidence interval.

5. Model-specific calibration logic

Kimi Code 2.7

Dense long-context attention makes \(B_{\mathrm{HBM}}\) large. The native-INT4 checkpoint uses 595.2 GB before runtime allocations, so it is split across two nodes. PP8 needs several independent sequences to fill its eight stages; one-user decode uses only one TP2 pair at a time and is approximately four times slower than the earlier PP2×TP8 one-user path.

GLM-5.3

Its native sparse indexer already reduces attention work. The 755.6 GB FP8 checkpoint must span two nodes, and software FP8-to-BF16 conversion on SM80 increases the weight path relative to the earlier ideal-W4 baseline. Pipeline overlap raises aggregate throughput, while the corrected model prevents unrelated requests from reducing one user's TPOT.

DeepSeek V4 Flash

The trained compressed/sparse cache already makes \(B_{\mathrm{HBM}}\) small. Its 159.6 GB mixed FP4/FP8 checkpoint permits two four-GPU replicas, but conversion to BF16 reduces their rates by roughly 3–9% versus the earlier ideal-W4 curves.

6. Cold-start TTFT

Let \(T_0(N)\) be the estimated single-request prefill time and let \(R\) be the number of model replicas. For a simultaneous closed burst of \(C\) requests, balanced across replicas, define

\[ c_r=\left\lceil\frac{C}{R}\right\rceil. \]

If full-length prompts already saturate each replica and the scheduler minimizes mean first-token time by completing prefills in first-token-priority order, then

\[ \overline{\mathrm{TTFT}}_{\mathrm{burst}} \approx T_0(N)\frac{c_r+1}{2}, \qquad \mathrm{TTFT}_{\mathrm{last}} \approx T_0(N)c_r. \]

Long prompts are split into 4K-token prefill chunks, giving about 18/32/64 microbatches at 72K/128K/256K. PP8 prefill efficiency is therefore approximately \(18/25\), \(32/39\), and \(64/71\), so the revised single-user centers are \(7.5/16.6/43.2\) s for Kimi, \(8.0/14.3/28.7\) s for GLM, and \(4.1/7.3/14.6\) s for V4 Flash. These are optimistic custom-runtime centers, not measured results.

\[ T_{\mathrm{complete},512} \approx \overline{\mathrm{TTFT}}_{\mathrm{burst}} +511\frac{\mathrm{TPOT}}{1000}. \]

7. Why full utilization is not an SLO

The graph's 100% point is a finite, closed batch. A continuously arriving service is different. A generic queueing approximation contains the factor

\[ W_q \propto \frac{\rho}{1-\rho}, \qquad \lim_{\rho\to1^-}W_q=\infty, \]

where \(\rho\) is offered utilization. Real long-prompt service times are highly variable, so the exact queue is not this simple; the divergence is the reason to preserve 25–50% operational headroom for prefills, misses, and burst absorption.

Uncertainty and exclusions

  • Not an A800 or full-model benchmark: A100 synthetic measurements ground the incremental H2D/P2P/FP8-KV path, but the simulator's p10–p90 band does not cover A100→A800 topology error or unmeasured frontier-model kernels. Core TPOT and cold TTFT can still be wrong by at least ±50%.
  • Steady decode and cold prefill are separated: the decode graphs assume requests have completed prefill. Mixing new 72K/128K/256K prefills into a full decode batch will cause TPOT spikes unless capacity is reserved.
  • Checkpoint bytes are measured, runtime bytes are modeled: official safetensor totals are 595.2 GB for Kimi, 755.6 GB for GLM, and 159.6 GB for V4 Flash. Allocator alignment, duplicated metadata, kernels, and communication workspaces can raise HBM use.
  • Pipeline topology is assumed: Kimi and GLM use PP8×TP2, with stages 1–4 on one node and 5–8 on the other. The central curve uses one independently schedulable request per decode microbatch; larger microbatches increase bubbles.
  • Stages must be time-balanced: equal layer counts need not mean equal work in a heterogeneous MoE model. The runtime should choose contiguous boundaries from measured stage time and weight footprint; the slowest stage sets pipeline cadence.
  • Host RAM matters: each node is assumed to have 1 TB. Official weight staging and exact caches must remain node-local to their pipeline stage and be released or streamed carefully.
  • Quality is assumed: the analysis does not prove that a fixed 1.56% selection policy preserves accuracy on these models and workloads.
  • Excluded latency: tokenization, API/network transit, detokenization, request logging, failures, retries, and multi-tenant isolation are not included.

Case A uses an advisory one-token-ahead oracle with 80% recall and 80% precision over the 40% miss set left after temporal reuse. Current-token landmark verification remains on the critical path.
