# A800 ShadowKV deployment case

[Open the interactive report](a800-pp8-tp2-shadowkv.html)

This case covers 72K, 128K, and 256K inputs; token-ahead, fetch-at-decode, and
no-ShadowKV native-cache serving; BF16 and FP8 KV storage; 1/2 accepted-token MTP
cases; 0–100% whole-layer ShadowKV residency; and one-user through 100%-of-admission
load. The native-cache control rejects the first request that exceeds its HBM limit.

## Pipeline revision

The former manually calibrated model-forward arrays have been removed. Official
model configs now feed a GenZ roofline, the 1–1,152-sequence sweep is emitted as a
LLMServingSim profile bundle, and the estimator obtains the model-forward value
through LLMServingSim's interpolation code. ShadowKV events are then added for Cases
A/B. Case C instead adds an explicit native-attention compute/HBM/dequant roofline.

Central hardware inputs are the measured A100-SXM4 envelope: 1,765 GB/s streaming
HBM, 51.6% median GEMM MBU, 455 Gvalue/s fused FP8 conversion, 22.0 GB/s single-GPU
H2D, 25.4 GB/s concurrent TP2 H2D, and measured P2P latency/bandwidth. BF16 compute
efficiency is the 40% GenZ A100 prior.

## Targets

- Kimi Code 2.7: PP8×TP2 across two servers.
- GLM-5.3: PP8×TP2 across two servers.
- GLM-5.3-Flash: one TP8 replica on one server. Only 11 DSA layers use ShadowKV;
  34 KDA layers keep recurrent state in HBM.
- DeepSeek V4 Flash: two TP4 replicas on one server.

## No-ShadowKV memory admission

These are memory-only whole-request ceilings at 72K/128K/256K. The calculation uses
90% of each 80 GiB GPU, subtracts official-format weights and a 6 GiB/GPU runtime
reserve, and keeps the complete native growing cache in HBM. It preserves trained
DSA/KDA/compressed-attention layouts rather than treating every model as dense.

| Model | BF16 KV | FP8 KV |
|---|---:|---:|
| Kimi Code 2.7 | 99 / 55 / 27 | 192 / 108 / 54 |
| GLM-5.3 | 52 / 29 / 14 | 101 / 56 / 28 |
| GLM-5.3-Flash | 270 / 152 / 76 | 524 / 294 / 147 |
| DeepSeek V4 Flash, two replicas | 482 / 272 / 136 | 936 / 528 / 264 |

The first request above each value is rejected; the model does not silently offload
or queue its KV state. These maxima are not latency recommendations.

For PP8 targets, the scheduler searches microbatch sizes up to the largest value that
still provides eight request groups. At full admission it selects 6/4/2 sequences for
Kimi 72K/128K/256K and 6/5/4 for GLM. Pipeline overlap raises aggregate throughput;
larger loads still touch more distinct experts, so per-user throughput falls.

## Generated core floors

One-sequence model-forward centers are about 40.9 ms for Kimi, 53.2 ms for GLM,
43.6 ms for GLM Flash, and 23.1 ms for each V4 Flash replica. At high load the MoE
curves rise; for example GLM reaches about 598 ms for 40 sequences before ShadowKV
events.

These are GenZ chunked-prefill rooflines. Cold simultaneous bursts use a
first-token-priority queue approximation and can still wait minutes at the largest
displayed loads.

## Interpretation

GLM Flash and DeepSeek V4 Flash are the best latency candidates in this model. The
original GLM and Kimi obtain large memory-capacity benefits from offloading, but their
large-batch MoE weight traffic dominates enough that 1.56% KV access does not imply
high per-user decode speed.

The p10–p90 bands are sensitivity intervals, not confidence intervals. No full model
was executed; routing skew, kernel fusion quality, real TP8 collectives, and A800
software behavior can move results by at least ±50%.
