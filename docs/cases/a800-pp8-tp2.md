# A800 PP8×TP2 ShadowKV-style offload

This case estimates 72K/128K/256K deployment behavior under official compressed model
weights, BF16 compute, 1.56% selected KV, and a custom runtime on A800.

[Open the interactive report](a800-pp8-tp2-shadowkv.html). It contains BF16/FP8 KV
switches, token-ahead/fetch-at-decode pages, all load points, TTFT, TPOT, aggregate
and per-user throughput, separate MTP accepted-prefix plots, a whole-layer HBM-residency
scan, expandable equations, and uncertainty notes.

## Topology

- Kimi Code 2.7 and GLM-5.3: PP8×TP2 across 16 GPUs on two servers.
- Stages 1–4: server A; stages 5–8: server B.
- One cross-server BF16 activation boundary; six local NVLink boundaries.
- Exact cache is split by layer ownership between the two host-memory pools.
- DeepSeek V4 Flash remains two four-GPU replicas on one server.

## LLMServingSim-extension FP8-KV central estimates

The pinned LLMServingSim frontend supplies transformer-block pipeline boundaries and
serving-trace conventions. An external ShadowKV trace layer adds per-block landmark
selection, overlapping key reconstruction/value fetch, stage-local PCIe and host-DRAM
limits, temporal reuse, and an optional advisory oracle. The central oracle has 80%
recall and 80% precision over entries not covered by 60% temporal reuse. Landmark
selection still verifies the current token, so this is not a magical full oracle.

Values show the 50%-load point followed by the full-admission point. Throughput is
formatted as total/per-user tokens per second.

## MTP overlay

The MTP graphs are deliberately separate from the no-MTP graphs. GLM uses a
three-token speculative block and V4 Flash uses two. The two displayed cases assume
a mean **consecutively accepted prefix** of one or two tokens; every other drafted
position still pays target verification. Kimi has no checkpoint MTP component.

At full-load FP8 with token-ahead cache prefetch, accepted-prefix-one produces
131/88/44 tok/s for GLM and 689/488/360 tok/s for V4 Flash at 72K/128K/256K.
Accepted-prefix-two produces 197/132/66 tok/s for GLM and 1,034/731/540 tok/s for
V4 Flash. These numbers are model-sensitive because the cache oracle covers only the
first verification position.

## Whole-layer HBM residency scan

The report evaluates requested resident ratios from 0% through 100% in ten-point
increments. Each request is rounded to a whole number of cache-bearing layers, and
the plots use the exact resulting ratios. Dashed connecting segments are interpolation;
only markers are directly modeled placements. A separate load slider covers one user
and 10% through 100% of the admission ceiling.

At 50% load with FP8 and token-ahead prefetch, moving from all-offloaded to all-resident
exact KV raises aggregate throughput by about 9%/8%/7% for Kimi at 72K/128K/256K,
6%/6%/4% for GLM, and 6%/6%/7% for V4 Flash. GLM 256K at full load barely fits
the optimistic FP8 planning envelope at 100% residency but exceeds it with BF16 KV;
the interactive report marks infeasible placements with hollow points.

## Main conclusion

The oracle hides most miss materialization but cannot hide current-token verification.
On the central trace, the advisory oracle raises full-load FP8 throughput over
fetch-at-decode by about 8%/8%/7% for Kimi, 5%/7%/8% for GLM, and 3%/4%/7%
for V4 Flash at 72K/128K/256K. GLM remains the weakest latency candidate because
extrapolated ShadowKV selector cost is paid across 78 cache-bearing blocks.

## Uncertainty

- The generated 256-sample p10–p90 range is parameter sensitivity, not confidence.
- Architecture mismatch and missing native A800 profiles can still move TPOT by ≥50%.
- Cold TTFT: at least ±50%.
- The fixed 1.56% policy is assumed to preserve quality; this case does not prove it.
- Unfused weight or FP8-KV conversion can invalidate both performance and memory use.
