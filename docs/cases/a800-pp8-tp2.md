# A800 PP8×TP2 ShadowKV-style offload

This case estimates 128K/256K deployment behavior under official compressed model
weights, BF16 compute, 1.56% selected KV, and a custom runtime on A800.

[Open the interactive report](a800-pp8-tp2-shadowkv.html). It contains BF16/FP8 KV
switches, token-ahead/fetch-at-decode pages, all load points, TTFT, TPOT, aggregate
and per-user throughput, expandable equations, and uncertainty notes.

## Topology

- Kimi Code 2.7 and GLM-5.3: PP8×TP2 across 16 GPUs on two servers.
- Stages 1–4: server A; stages 5–8: server B.
- One cross-server BF16 activation boundary; six local NVLink boundaries.
- Exact cache is split by layer ownership between the two host-memory pools.
- DeepSeek V4 Flash remains two four-GPU replicas on one server.

## Main conclusion

PP8×TP2 preserves per-GPU weight/cache bytes but trades low-load latency for
high-concurrency utilization. A lone Kimi/GLM decoder activates one two-GPU stage
at a time. Independent requests fill the pipeline, so per-user speed initially
improves with concurrency and later declines under contention.

Against PP2×TP8 at full admission, the modeled aggregate-throughput reductions are
about 15%/26% for Kimi and 10%/14% for GLM at 128K/256K. Those differences are
pipeline bubbles, not additional KV traffic.

## Uncertainty

- Token-ahead aggregate throughput and TPOT: approximately ±30–50%.
- Fetch-at-decode throughput and TPOT: approximately ±40–60%.
- Cold TTFT: at least ±50%.
- The fixed 1.56% policy is assumed to preserve quality; this case does not prove it.
- Unfused weight or FP8-KV conversion can invalidate both performance and memory use.
