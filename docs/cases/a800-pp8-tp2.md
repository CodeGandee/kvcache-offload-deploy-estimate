# A800 ShadowKV deployment case

[Open the interactive report](a800-pp8-tp2-shadowkv.html)

This case covers 72K, 128K, and 256K inputs; token-ahead, fetch-at-decode, and
no-ShadowKV native-cache serving; BF16 and FP8 KV storage; 1/2 accepted-token MTP
cases; 0–100% whole-layer ShadowKV residency; and one-user through 100%-of-admission
load. Every case rejects the first request that exceeds its HBM limit. System-RAM
capacity is unbounded for admission, although finite host-transfer bandwidth remains
in the ShadowKV latency model.

## Pipeline revision

The former manually calibrated model-forward arrays have been removed. Official
model configs now feed a GenZ roofline, the 1–4,096-sequence sweep is emitted as a
LLMServingSim profile bundle, and the estimator obtains the model-forward value
through LLMServingSim's interpolation code. ShadowKV selection, overlapped
materialization, and the separate Table-13 sparse-attention term are then added for
Cases A/B; V4 layers outside the overlay retain native attention. Case C instead adds
the full native-attention compute/HBM/dequant roofline. Both paths separately charge
the GLM-Flash KDA recurrent-state update lower bound.

Central hardware inputs are the measured A100-SXM4 envelope: 1,765 GB/s streaming
HBM, 51.6% median GEMM MBU, 455 Gvalue/s fused FP8 conversion, 22.0 GB/s single-GPU
H2D, 25.4 GB/s concurrent TP2 H2D, and measured P2P latency/bandwidth. BF16 compute
efficiency is the 40% GenZ A100 prior.

## Memory-accounting correction

This revision retires the earlier assumption that TP2/TP8 automatically divides an
MLA cache. In the stated pure-TP topology (DCP1), each TP rank needs the complete
latent history for its PP-owned layers. The same applies to model-native sparse-index
rows and, in this ShadowKV adapter, the rank-160/landmark/sparse working state and
selected H2D payload. Attention FLOPs remain head-sharded; GLM-Flash's fixed KDA head
state is also TP-sharded.

The index and KDA formats are no longer scaled by the main-cache toggle. GLM variants
use 132 bytes per index entry (128 FP8 values plus one FP32 scale), V4's checked-in
reference uses a 256-byte BF16 index row, and every GLM-Flash KDA layer has a 4 MiB
FP32 recurrent matrix plus about 0.140625 MiB of BF16 convolution state before TP8
sharding. The graphs, load points, microbatches, TTFT bursts, TPOT, throughput, MTP,
and residency feasibility have all been regenerated from this accounting.

Explicit DCP could reduce sequence-growing state, but also adds distributed selector
and partial-attention communication. It is not represented by the old `/TP` curves
and remains a separate future case.

The implementation is cross-checked against full-model 256K BF16 logical totals
before applying placement: 17.15625 GiB for Kimi, 22.61426 GiB for GLM including its
index, and 2.97610 GiB for GLM Flash including its pooled index and fixed KDA state.
PP slices these totals by owned layers; pure TP replicates the MLA/index portion.

## Targets

- Kimi Code 2.7: PP8×TP2 across two servers.
- GLM-5.3: PP8×TP2 across two servers.
- GLM-5.3-Flash: one TP8 replica on one server. Only 11 DSA layers use ShadowKV;
  34 KDA layers keep recurrent state in HBM.
- DeepSeek V4 Flash: two TP4 replicas on one server.

## HBM-only memory admission

ShadowKV's cap includes rank-160 key factors, chunk-8 landmarks, the sparse exact
buffer, retained native sparse-index rows, any native state outside the overlay,
GLM-Flash's fixed KDA state, official-format weights, and the runtime reserve. It does
not count the exact offloaded cache against system-RAM capacity. The default is pure
TP with DCP1: every layer on the busiest PP stage is included and MLA/latent history
is replicated on each TP rank. For Kimi 128K FP8 that means eight layers and 0.2456
GiB/request/GPU for ShadowKV, versus 0.5801 GiB for native cache; the corresponding
ceilings are 127 and 54 users. There is no division by TP2.

These are memory-only whole-request ceilings at 72K/128K/256K. The calculation uses

For PP8 targets, the scheduler searches microbatch sizes up to the largest value that
still provides eight request groups. Pipeline overlap raises aggregate throughput;
the very large HBM-feasible batches still touch more distinct experts and divide the
result among more users, so per-user throughput falls sharply near OOM.

## Generated core floors

One-sequence model-forward centers are about 40.9 ms for Kimi, 53.2 ms for GLM,
43.6 ms for GLM Flash, and 23.1 ms for each V4 Flash replica. At high load the MoE
curves rise; for example GLM reaches about 598 ms for 40 sequences before ShadowKV
events.

## Interpretation

GLM Flash and DeepSeek V4 Flash are the best latency candidates in this model. The
original GLM and Kimi obtain large memory-capacity benefits from offloading, but their
large-batch MoE weight traffic dominates enough that 1.56% KV access does not imply
high per-user decode speed.

The p10–p90 bands are sensitivity intervals, not confidence intervals. No full model
was executed; routing skew, kernel fusion quality, real TP8 collectives, and A800
software behavior can move results by at least ±50%.
